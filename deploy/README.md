# آماده‌سازی نسخه آزمایشی برای انتشار

این پوشه بسته تنظیمات و چک‌لیست انتشار است، نه نصب‌کننده خودکار و نه تأیید آمادگی فروش. فعلاً سرور و دامنه انتخاب نشده‌اند. تنظیمات محلی XAMPP نباید با نمونه‌های این پوشه جایگزین شوند.

## نتیجه این مرحله — ۲۰۲۶/۰۹/۰۵

- خطای SQL در تغییر پلن مشتری اصلاح شد. قفل تراکنشی مشتری در همین API مانع هم‌پوشانی دو درخواست تغییر پلن می‌شود؛ این ادعا شامل تمام مسیرهای مدیریت اشتراک نیست.
- تست HTTP اختصاصی، ایجاد اشتراک، تغییر پلن، لغو اشتراک قبلی، عدم تکرار در درخواست یکسان، رد پلن غیرفعال، CSRF و تعداد رویدادهای Audit را بررسی می‌کند.
- بررسی تنظیمات انتشار بدون اتصال به دیتابیس یا شبکه انجام می‌شود و مقادیر رمزها را چاپ نمی‌کند.
- تأیید تنظیمات به معنی تأیید امنیت سرور، عملکرد پرداخت، جداسازی کامل مشتریان، ظرفیت هم‌زمان یا امکان بازیابی نیست.

نتیجه اجرای محلی در همین تاریخ: بررسی نحوی ۲۵۰ فایل PHP بدون خطا؛ ۳۱ بررسی ابزار preflight، ۱۴ بررسی HTTP تغییر پلن، تست auth/cookie/CSRF/SSE، ۱۶ بررسی runtime و ۳۹ بررسی دیتابیس موفق بودند. `npm run lint` و `npm run build` نیز موفق شدند. build با تنظیمات محلی ساخته شده، نه دامنه staging. تست تصویری مرورگر، فشار هم‌زمان و بازیابی بکاپ در این مرحله اجرا نشده‌اند.

پیش‌بررسی روی فایل‌های نمونه با خروجی ۱ و ۱۲ ایراد موردانتظار (دامنه/رمز نمونه) رد شد. روی تنظیمات محلی، خواندن سخت‌گیرانه در سطر ۶۰ `backend/.env` با خروجی ۲ متوقف شد: خط قالب `KEY=value` ندارد؛ بارگذار فعلی برنامه چنین خطی را نادیده می‌گیرد. فایل محرمانه محلی دست‌نخورده مانده است. هنگام تهیه فایل مقصد، متن توضیحی باید با `#` شروع شود و فایل دوباره بررسی شود.

## ۱. تنظیمات نسخه آزمایشی

پیش از خرید، [مشخصات میزبانی و متن استعلام فروشنده](HOSTING.md) را بررسی کنید؛ داشتن cPanel به‌تنهایی سازگاری با پروژه را تضمین نمی‌کند.

توپولوژی این نسخه: پنل و API روی یک مبدأ HTTPS؛ مثلاً پنل در `https://app.example.com` و API در `/backend/api`. این دامنه فقط نمونه است و عمداً از بررسی انتشار عبور نمی‌کند. معماری چنددامنه‌ای به آزمون جداگانه Cookie و CORS نیاز دارد.

از `backend.env.example` و `frontend.env.example` کپی جداگانه و خارج از مخزن بسازید. دامنه واقعی، دیتابیس مجزا و رمزها را در همان کپی تنظیم کنید. فایل محرمانه، بکاپ واقعی و خروجی SQL مشتری را وارد Git نکنید. بررسی تنظیمات را از ریشه پروژه اجرا کنید:

```powershell
php backend/cli/release-preflight.php --env C:/secure/staging/backend.env --frontend-env C:/secure/staging/frontend.env --json
```

مسیرهای بالا فرضی‌اند. در ویندوز اگر PHP در PATH نیست، از `C:/xampp/php/php.exe` استفاده کنید. در حالت `--env` فقط فایل‌های معرفی‌شده بررسی می‌شوند، نه متغیرهای محیطی پردازش. بدون این گزینه، فایل‌های فعلی `backend/.env` و `frontend/.env.local` همراه با اولویت متغیرهای پردازش بررسی می‌شوند؛ این نتیجه جایگزین بررسی محیط واقعی PHP-FPM و محیط build نیست.

خروجی صفر یعنی تمام بررسی‌های تنظیمات قبول شده‌اند؛ خروجی ۱ یعنی تنظیمات با پروفایل انتشار سازگار نیستند؛ خروجی ۲ یعنی ورودی یا فایل تنظیمات معتبر نیست. نمونه‌های این پوشه تا زمان جایگزینی دامنه و رمزها باید رد شوند. فایل‌ها باید قالب ساده `KEY=value` داشته باشند؛ توضیح با `#` شروع شود، کلید تکراری، interpolation و مقدار چندخطی پشتیبانی نمی‌شود. خطای قالب فقط شماره خط را نمایش می‌دهد. تنظیمات فعلی محلی می‌توانند عمداً از این بررسی عبور نکنند.

نکات مهم:

- روی staging نیز `APP_ENV=production` و `APP_DEBUG=false` باشد؛ داده‌ها مستقل و آزمایشی باشند.
- سه کلید JWT، رمزنگاری و heartbeat باید مستقل و تصادفی باشند. حداقل طول و تنوع کاراکتر در ابزار فقط تشخیص ابتدایی است، نه تضمین کیفیت رمز. تولید را در محیط امن انجام دهید و کلید را در چت نفرستید.
- `APP_ENCRYPTION_KEY` را همراه با برنامه بازیابی نگه دارید. تعویض بدون برنامه آن می‌تواند داده‌های رمز‌شده، از جمله اطلاعات 2FA، را غیرقابل‌استفاده کند.
- کاربر دیتابیس اختصاصی و غیر-root باشد؛ سطح دسترسی واقعی با بررسی نام کاربری مشخص نمی‌شود و باید روی سرور کنترل شود.
- کوکی امن و host-only، CORS با مبدأ دقیق، و `WIDGET_ALLOW_EMPTY_ORIGIN=false` ضروری‌اند. دامنه مشتری در تنظیمات همان سایت ثبت شود؛ لیست عمومی `WIDGET_ALLOWED_ORIGINS` خالی بماند، چون ورودی عمومی برای همه سایت‌ها معتبر است.
- زمان نشست نمونه یک ساعت است و پس از انقضا ورود مجدد لازم می‌شود؛ تمدید خودکار نشست را مفروض نگیرید.
- نمونه هیچ سرویس بیرونی هوش مصنوعی یا درگاه پرداختی را فعال نمی‌کند.

## ۲. ساخت و اتصال سرویس‌ها

بعد از انتخاب میزبان، نسخه‌های runtime و افزونه‌ها با محیط مقصد بررسی شوند. تست محلی روی PHP 8.2.12 و MariaDB 10.4.32 انجام شده است؛ این نسخه‌ها الزام یا پیشنهاد برای سرور عمومی نیستند. نسخه پشتیبانی‌شده مقصد باید جداگانه انتخاب و آزمایش شود.

در پوشه `frontend`، وابستگی‌های قفل‌شده با `npm ci` نصب، مقدار `NEXT_PUBLIC_API_BASE_URL` قبل از build تنظیم، و سپس `npm run lint` و `npm run build` اجرا شود. نسخه منتشرشده با `npm run start` اجرا شود، نه `npm run dev`. تغییر متغیر عمومی API پس از build کافی نیست و build مجدد لازم است. هیچ کلید محرمانه‌ای در متغیرهای `NEXT_PUBLIC_*` قرار نگیرد.

وب‌سرور باید این مسیرها را صریحاً نگاشت کند:

- مسیر `/backend/api/` به API واقعی PHP؛ اجرای PHP فقط در محل‌های تأییدشده.
- `/widget.js` به فایل `widget/dist/widget.js` همین نسخه.
- سایر مسیرهای پنل به سرویس Next.
- آپلودهای موردنیاز به فضای پایدار، بدون اجازه اجرای اسکریپت و بدون فهرست‌کردن پوشه.

ریشه کل مخزن را منتشر نکنید. `.git`، فایل‌های env، `config`، `includes`، `cli`، `cron`، `database`، `storage`، مستندات و فایل‌های استقرار نباید از وب قابل دریافت باشند. فایل‌های QA در `uploads/qa-artifacts` نیز خصوصی بمانند. به `.htaccess` به‌تنهایی تکیه نکنید؛ میزبان ممکن است آن را اجرا نکند. دریافت مستقیم فایل‌های حساس و اجرای فایل در uploads باید عملاً رد شود.

با تنظیمات پیش‌فرض، آپلود چت در `backend/uploads/chat` ذخیره می‌شود و URL عمومی با افزودن `/uploads/chat/...` به `UPLOAD_PUBLIC_URL` ساخته می‌شود. اگر `UPLOAD_STORAGE_ROOT` تغییر کند، مسیر ذخیره و نگاشت وب باید با هم آزمایش شوند. داده‌های آپلود نباید با تعویض نسخه پاک شوند. این تنظیمات به‌تنهایی فایل‌های فعلی را خصوصی یا وابسته به نشست نمی‌کنند؛ نیاز محصول به پیوست خصوصی قبل از فروش بررسی شود.

برای SSE، buffering و timeout پروکسی با طول stream هماهنگ شوند و قطع/اتصال مجدد، شبکه ضعیف و چند گفتگو هم‌زمان آزموده شوند. فایل دقیق وب‌سرور و سرویس‌ها بعد از مشخص‌شدن سیستم‌عامل و پنل میزبان تهیه خواهد شد؛ هنوز چنین تنظیماتی نصب نشده‌اند.

## ۳. دیتابیس، نصب اولیه و بازگشت نسخه

`backend/database/schema.sql` ساختار پاک‌شده دیتابیس است. وجود آن به معنی نصب اولیه کامل نیست: نقش‌ها، مجوزها، پلن‌ها و اولین مدیر باید با فرآیند bootstrap کنترل‌شده ایجاد و بررسی شوند؛ از dump حاوی مشتریان و رمزهای محیط فعلی برای ساخت staging استفاده نکنید.

روی دیتابیس موجود، تمام migrationها را کورکورانه و دوباره اجرا نکنید. ابتدا نسخه فعلی، تغییرات واقعاً لازم و بکاپ مشخص شوند. نصب از صفر و ارتقای دیتابیس موجود هر دو باید روی دیتابیس آزمایشی جداگانه تأیید شوند. در این مرحله schema و داده‌های واقعی کسب‌وکار تغییر داده نشده‌اند؛ تست HTTP فقط fixtureهای موقت ایجاد و حذف می‌کند و ممکن است لاگ عملیاتی درخواست باقی بگذارد.

قبل از هر انتشار، نسخه کد/build، بکاپ دیتابیس، آپلودها و تنظیمات لازم برای بازیابی مشخص باشند. یک نسخه رمز‌شده خارج از سرور نگه دارید؛ کلید بازیابی را در همان محل عمومی بکاپ قرار ندهید. بازیابی فقط روی مقصد آزمایشی مستقل انجام شود و ورود، گفتگو و دانلود پیوست پس از آن بررسی شوند. موفقیت گرفتن dump به‌تنهایی تست بازیابی نیست. بازگرداندن build قبلی بدون بررسی سازگاری دیتابیس کافی نیست.

## ۴. کارهای زمان‌بندی‌شده

پس از استقرار، این دو فرمان با کاربر سرویس، محیط صحیح، ثبت خروجی و جلوگیری از اجرای هم‌پوشان، هر دقیقه زمان‌بندی شوند:

```text
php backend/cron/automation-worker.php
php backend/cron/system-heartbeat.php scheduler
```

فرمان heartbeat فقط زنده‌بودن زمان‌بند را ثبت می‌کند؛ برای سالم نشان‌دادن worker خراب از آن استفاده نکنید. worker اتوماسیون وضعیت خودش را ثبت می‌کند. تست شکست و گزارش وضعیت نیز لازم است. در این مرحله job جدید یا پنجره پس‌زمینه‌ای نصب/اجرا نشده است.

`operations-cleanup.php` داده حذف می‌کند و اکنون اجرا نشده است. تنها بعد از توافق درباره نگهداری داده و بکاپ زمان‌بندی شود: لاگ درخواست ۳۰ روز، خطای حل‌شده ۹۰ روز، تلاش ورود ۱۸۰ روز، رویداد امنیتی حل‌شده ۳۶۵ روز؛ نشست‌های منقضی/لغوشده و rate limit نیز قواعد جدا دارند. کد فایل پیش از فعال‌سازی بازبینی شود.

## ۵. آزمون‌های قابل تکرار روی محیط محلی

از ریشه پروژه و با Apache/MariaDB روشن:

```text
php backend/cli/release-preflight-test.php
php backend/cli/pass2-runtime-check.php
php backend/cli/pass2-database-check.php
php backend/cli/customer-plan-smoke-test.php
php backend/cli/plan-change-test.php
php backend/cli/auth-cookie-smoke-test.php
```

دو تست آخر داده مصنوعی ایجاد می‌کنند و در `finally` پاک می‌کنند؛ در production از اجرا امتناع می‌کنند. تست پلن نشست را مستقیم برای مدیر مصنوعی صادر می‌کند و تست ورود نیست؛ تست auth مسیر ورود/خروج را پوشش می‌دهد. اجرای اجباری یا متوقف‌کردن پردازش قبل از `finally` ممکن است به بررسی و پاک‌سازی دستی همان fixtureها نیاز داشته باشد. روی سرور مشتری تست نوشتنی اجرا نکنید.

## ۶. دروازه‌های باقی‌مانده قبل از فروش

- [ ] انتخاب سرور/دامنه، HTTPS واقعی و حفاظت مسیرهای داخلی.
- [ ] نصب پاک و ارتقای آزمایشی دیتابیس، ایجاد امن اولین Owner و فعال‌سازی 2FA همراه با نگهداری کدهای بازیابی.
- [ ] بازبینی امنیتی جداسازی مشتری‌ها، مجوزها، آپلود، نشست و نقاط نمایش HTML؛ تست موفق محلی جایگزین این بازبینی نیست.
- [x] اصلاح مسیر تغییر پلن با تأیید کاربر: انتخاب ماهانه/سه‌ماهه/سالانه و ورود صریح مبلغ کل به ریال؛ شروع از زمان ثبت، لغو اشتراک جاری و ثبت اشتراک جدید بدون ثبت پرداخت یا تمدید خودکار. جزئیات در بخش ۸.
- [x] یکسان‌سازی قیمت کاتالوگ پلن‌ها: ذخیره ریال، نمایش و ویرایش کاتالوگ به تومان با تبدیل صریح. مبالغ تاریخی اشتراک/پرداخت با واحد ثبت‌شده خودشان باقی می‌مانند؛ هیچ تبدیل دسته‌جمعی روی سوابق انجام نشده است. جزئیات در بخش ۹.
- [ ] تأیید ثبت پرداخت، انقضا، تعلیق، تمدید و سقف مصرف؛ ثبت دستی پرداخت به معنی اتصال به درگاه نیست.
- [ ] آزمون مرورگر برای مشتری/اپراتور/مدیر و ویجت روی دامنه مشتری، دسکتاپ و موبایل؛ آزمون reconnect و اعلان‌ها.
- [ ] استقلال چت از اینترنت بین‌الملل — فعلاً در فهرست کارها، نه در حال پیاده‌سازی؛ پیش از هر ادعای تبلیغاتی، معیارهای بخش ۷ تأیید شوند.
- [ ] تست بار متناسب با تعداد مشتری هدف؛ هنوز ظرفیت هم‌زمان تضمین نشده است.
- [ ] یک بازیابی کامل و یک تمرین rollback، همراه با ثبت نتیجه و زمان بازیابی.
- [ ] تعریف شرایط خدمات، حریم خصوصی، نگهداری داده و فرآیند پاسخ‌گویی پشتیبانی برای عرضه واقعی.

پس از عبور از این موارد می‌توان درباره عرضه آزمایشی محدود تصمیم گرفت؛ این مرحله به‌تنهایی مجوز اعلام «آماده فروش عمومی» نیست.

## ۷. کار برنامه‌ریزی‌شده: چت در شبکه داخلی

ثبت‌شده به درخواست کاربر در ۲۰۲۶/۰۹/۰۵؛ فعلاً به تعویق افتاده و ادامه آماده‌سازی انتشار اولویت دارد. وجود اتصال مجدد و fallback دریافت پیام در ویجت به معنی تأیید عملکرد در محدودیت واقعی شبکه نیست.

- [ ] بررسی دسترسی داخلی سایت میزبان، فایل ویجت، API، پنل اپراتور، DNS، CDN احتمالی و پیوست‌ها؛ مسیر حیاتی نباید به سرویس خارجی وابسته باشد.
- [ ] بررسی صفحه پشتیبانی مستقل به‌عنوان مسیر جایگزین برای مشتریانی که سایت اصلی‌شان در دسترس نیست؛ اطلاع‌رسانی آدرس پیش از اختلال.
- [ ] نمایش وضعیت واقعی اتصال، حفظ پیش‌نویس و پیام ارسال‌نشده، تلاش مجدد امن و جلوگیری از ثبت تکراری پیام؛ ذخیره محلی نباید به‌عنوان تحویل به سرور نمایش داده شود.
- [ ] آزمون مسدودبودن ارتباط بین‌الملل از سمت مرورگر و سرور، با مرورگر بدون کش: شروع گفتگو، پیام دوطرفه، ورود اپراتور، پیوست و قطع/اتصال مجدد.
- [ ] بررسی روی چند اپراتور داخلی پس از استقرار و ثبت نتایج و محدودیت‌ها؛ شبیه‌سازی به‌تنهایی تضمین اختلال‌های واقعی نیست.

دامنه این کار فعلاً چت است؛ دسترسی به منابع خارجی برای خزش یا سرویس‌های بیرونی آینده تضمین نمی‌شود. عبارت قابل ارزیابی برای معرفی محصول: «چت بدون وابستگی به اینترنت بین‌الملل، مشروط به دسترسی کاربران به شبکه داخلی و سرور سرویس». تا زمان تأیید آزمون‌ها این یک هدف محصول است، نه قابلیت تأییدشده یا تضمین عدم قطعی.

## ۸. تکمیل تغییر پلن — ۲۰۲۶/۰۹/۰۵

این بخش جایگزین رفتار یک‌ساله/مبلغ ماهانه توصیف‌شده در گزارش اولیه همین فایل است. فرم مدیریت مشتری اکنون مدت و مبلغ کل به ریال را از مدیر می‌گیرد و پیش از ثبت، خلاصه شرایط و اثر لغو اشتراک قبلی را برای تأیید نشان می‌دهد. پس از یکسان‌سازی قیمت کاتالوگ در بخش ۹، مبلغ پیشنهادی از قیمت ماهانه پلن و مدت انتخابی پر می‌شود و مدیر می‌تواند آن را تغییر دهد. داده‌ها و اشتراک‌های قبلی خودکار تبدیل یا اصلاح نشده‌اند؛ migration جدیدی لازم نیست.

API مدت، مبلغ اعشاری معتبر، تأیید صریح و پلن موردانتظار را کنترل می‌کند. درخواست قدیمی بدون این فیلدها رد می‌شود؛ صفحه و API باید با هم منتشر شوند. درخواست تکراری با شرایط یکسان اشتراک دیگری ایجاد نمی‌کند؛ درخواست همان پلن با شرایط متفاوت یا تغییر پلن از روی وضعیت قدیمی با خطای ۴۰۹ رد می‌شود. تغییر شرایط یا تمدید همان پلن همچنان از صفحه اشتراک‌ها انجام می‌شود. مبلغ پرداخت‌شده و اعتبار باقیمانده محاسبه یا مسترد نمی‌شوند و این موضوع در تأیید مدیر نوشته شده است.

پایان دوره با ماه تقویمی محاسبه می‌شود و روز آخر ماه کنترل می‌شود (مثلاً ۳۱ ژانویه به آخر فوریه). تست مستقل تاریخ/مبلغ با ۱۹ بررسی و تست HTTP با ۲۹ بررسی موفق شدند. تست HTTP شامل مبلغ دلخواه، مدت، رد شرایط نامعتبر، درخواست قدیمی/تکراری، عدم ثبت پرداخت و حفظ داده‌ها پس از درخواست ردشده است؛ fixtureهای مصنوعی حذف شدند. این تست، تست بار هم‌زمان چندپردازشی یا آزمون تصویری فرم نیست.

## ۹. قیمت‌گذاری اولیه — ۲۰۲۶/۰۹/۰۵

قیمت ماهانه Basic برابر ۳۹۰٬۰۰۰ تومان، Growth برابر ۸۹۰٬۰۰۰ تومان و Pro برابر ۱٬۹۹۰٬۰۰۰ تومان در دیتابیس محلی اعمال شد. پاسخ خودکار Growth فعال شد؛ ظرفیت سایت، اپراتور و گفتگو تغییر نکرد. اسکریپت اعمال قیمت در اجرای اول ۳ پلن را تغییر داد و در اجرای دوم هیچ تغییری نداد. اشتراک‌ها و پرداخت‌های واقعی تغییری نکردند.

صفحه عمومی اکنون قیمت و امکانات را از API پلن‌ها می‌خواند. API ایجاد/ویرایش پلن، واحد صریح `price_currency: IRR` می‌خواهد؛ نسخه فرانت‌اند و بک‌اند باید با هم منتشر شوند. فرم کاتالوگ تومان را به ریال تبدیل می‌کند. مبلغ پیشنهادی اشتراک برای سه‌ماهه و سالانه به‌ترتیب سه و دوازده برابر است، بدون تخفیف؛ برای ارزهای دیگر نرخ تبدیل فرضی تولید نمی‌شود.

آزمون این مرحله: ۳۵ بررسی HTTP پلن، ۲۵ بررسی تبدیل مبلغ، lint و build فرانت‌اند و بررسی نحوی فایل‌های PHP تغییرکرده موفق شدند. نمایش سه قیمت در صفحه عمومی مرورگر نیز تأیید شد. این بررسی مرورگر محدود به صفحه عمومی بود و جایگزین آزمون کامل نقش‌ها یا پرداخت نیست. سرور موقت مرورگر پس از تست بسته شد.

دستورها و محدودیت‌های اجرای قیمت‌گذاری در [راهنمای قیمت‌گذاری](PRICING.md) آمده است. دوره آزمایشی ۱۴روزه، تخفیف سالانه و درگاه پرداخت در این مرحله پیاده‌سازی نشده‌اند.
